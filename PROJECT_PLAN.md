# Family Budget — Project Plan

Статус проекта:
локальный браузерный калькулятор семейного бюджета, который постепенно преобразуется в mobile-first приложение.

Главная цель:
создать максимально простой семейный финансовый инструмент, удобный для ежедневного использования со смартфона и практически не требующий эксплуатационных расходов.

---

## Основные принципы

### 3.1. Local-first

По умолчанию данные пользователя хранятся локально.

На текущем этапе сервер, аккаунты пользователей и облачная синхронизация не требуются.

Добавление backend допускается только отдельным будущим решением владельца проекта.

### 3.2. Минимальные эксплуатационные расходы

Архитектура должна по возможности обходиться без:

* платных API;
* обязательного сервера;
* постоянной базы данных в облаке;
* AI API для повседневных операций;
* ежемесячных инфраструктурных расходов.

### 3.3. Mobile-first

Основной будущий сценарий использования — смартфон.

Desktop-версия при этом должна сохраниться и оставаться работоспособной.

Нельзя просто уменьшать desktop UI.

Для смартфона должен существовать отдельный UX, похожий на обычное мобильное приложение.

### 3.4. Сохранение бизнес-логики

Существующие:

* расчёты;
* счета;
* переводы;
* доходы;
* расходы;
* вклады;
* кредиты;
* финансовые цели;
* платежи;
* аналитика;
* резервные копии

не должны переписываться только ради изменения внешнего вида.

UI должен использовать существующую бизнес-логику.

### 3.5. Простота повседневного использования

Самое частое действие пользователя:

добавить расход или доход.

Оно должно выполняться максимально быстро.

Целевой сценарий:

открыть приложение → нажать "+" или микрофон → ввести/сказать операцию → подтвердить → закрыть приложение.

### 3.6. Безопасность изменений

Каждый этап выполняется отдельно.

После каждого этапа:

* запускаются тесты;
* проверяется desktop;
* проверяется mobile;
* составляется отчёт;
* работа останавливается до следующего решения владельца проекта.

## Целевая мобильная навигация

На смартфоне основной интерфейс должен иметь нижнюю фиксированную панель:

Главная | Операции | + | Цели | Ещё

### Главная

Показывает только наиболее важную информацию:

* доступный остаток;
* доходы текущего периода;
* расходы текущего периода;
* накопления;
* количество активных финансовых целей;
* последние операции.

Главная не должна превращаться в длинную аналитическую страницу.

### Операции

Содержит:

* расходы;
* доходы;
* поиск;
* фильтры;
* историю операций.

На мобильном таблицы должны в дальнейшем быть заменены карточками/лентой операций.

### Центральная кнопка "+"

Главное действие приложения.

В конечной архитектуре открывает быстрое добавление операции.

На первом этапе допускается переключение на раздел операций и переход к существующей форме.

### Цели

Содержит:

* накопительные цели;
* вклады;
* кредиты;
* связанные пополнения и платежи.

### Ещё

Содержит редко используемые функции:

* счета;
* переводы;
* аналитика;
* экспорт;
* импорт;
* резервные копии;
* печать;
* настройки;
* выбор темы;
* очистка данных.

## Дорожная карта

### Этап 0. Существующая функциональная база — DONE

Уже существуют:

* счета;
* переводы;
* доходы;
* расходы;
* финансовые цели;
* вклады;
* кредиты;
* платежи/пополнения;
* аналитика;
* светлая и тёмная темы;
* импорт;
* экспорт;
* резервная копия;
* локальное хранение;
* автоматические тесты;
* разделение JS на функциональные модули.

### Этап 1. Mobile App Shell — DONE

Цель:

превратить мобильный интерфейс из длинной desktop-страницы в оболочку мобильного приложения.

В рамках этапа:

* компактная мобильная шапка;
* нижняя фиксированная навигация;
* разделы:

  * Главная;
  * Операции;
  * Цели;
  * Ещё;
* центральная кнопка "+";
* скрытие старой верхней навигации на телефоне;
* отображение только активного мобильного раздела;
* сохранение существующего desktop UI;
* сохранение всей существующей функциональности.

Не входит:

* новый дизайн сводки;
* bottom sheet добавления операции;
* голосовой ввод;
* новая лента операций;
* PWA;
* IndexedDB.

### Этап 2. Mobile Dashboard — IN PROGRESS

Переделка главного экрана смартфона.

Вместо четырёх крупных последовательных карточек:

* один основной баланс;
* компактные показатели доходов/расходов;
* накопления;
* активные цели;
* последние операции.

Цель — наиболее важная финансовая информация должна помещаться примерно на одном мобильном экране.

Исправление единого порядка операций (Dashboard + вкладка «Операции») реализовано и ожидает пользовательской проверки.

### Этап 3. Быстрое добавление операции — NEXT

Создать мобильный bottom sheet / modal:

* расход / доход;
* сумма;
* категория;
* счёт;
* дата;
* дополнительные поля.

Автоматически подставлять:

* сегодняшнюю дату;
* последний используемый счёт;
* при возможности — последние значения.

Редко используемые поля убрать под "Дополнительно".

### Этап 4. Mobile Transaction Feed — PLANNED

На телефоне отказаться от desktop-таблицы операций.

Использовать мобильную ленту карточек.

Пример:

Продукты
Пятёрочка
Основная карта
−2 450 ₽

Desktop-таблицу сохранить для больших экранов.

### Этап 5. Mobile Goals & Accounts — PLANNED

Переработать мобильное представление:

* финансовых целей;
* вкладов;
* кредитов;
* счетов;
* переводов.

Формы не должны постоянно занимать экран.

Создание и редактирование открываются только по запросу пользователя.

### Этап 6. Voice Input v1 — PLANNED

Добавить голосовой ввод без обязательного AI API.

Целевой сценарий:

пользователь говорит:

"Продукты 2450 рублей с основной карты"

Система преобразует речь в текст и локально разбирает:

* тип операции;
* сумму;
* категорию;
* счёт;
* дату;
* комментарий при наличии.

Перед записью обязательно показать подтверждение.

Никогда автоматически не создавать финансовую операцию только по результату распознавания речи.

Архитектура:

Speech-to-Text
↓
текст
↓
локальный parser
↓
предпросмотр
↓
подтверждение пользователя
↓
сохранение операции

AI API на данном этапе не использовать.

### Этап 6.1. Локальный словарь привычек — PLANNED

Позволить системе запоминать типичные соответствия.

Пример:

Пятёрочка → Продукты
Лента → Продукты
Лукойл → Топливо
Яндекс Go → Транспорт

Словарь хранить локально.

В дальнейшем возможно автоматическое обучение словаря на исправлениях пользователя.

### Этап 7. PWA — PLANNED

Превратить веб-приложение в устанавливаемое Progressive Web App.

Предусмотреть:

* manifest;
* service worker;
* иконку;
* standalone display;
* работу с домашнего экрана телефона;
* базовый offline-режим.

Не переписывать приложение на React Native только ради установки на телефон.

Сначала проверить реальную эксплуатацию PWA.

### Этап 8. IndexedDB — PLANNED

После стабилизации интерфейса рассмотреть миграцию основного хранения:

localStorage → IndexedDB.

Причины:

* рост истории операций;
* структурированные данные;
* долгосрочное использование;
* будущая масштабируемость.

Миграция должна быть обратимо и безопасно спроектирована.

Нельзя потерять существующие пользовательские данные.

### Этап 9. Синхронизация нескольких устройств — OPTIONAL

Не реализовывать без отдельного решения владельца проекта.

Возможный будущий сценарий:

телефон одного члена семьи
↕
общие семейные данные
↕
телефон другого члена семьи

Такой режим потребует отдельного анализа:

* backend;
* аутентификация;
* база данных;
* безопасность;
* расходы;
* конфликты синхронизации.

До отдельного решения проект остаётся local-first.

## Архитектурные запреты

Без отдельного решения владельца проекта запрещено:

* подключать платные API;
* подключать AI API;
* создавать backend;
* создавать обязательную регистрацию;
* добавлять облачную БД;
* менять формат финансовых данных;
* удалять существующие возможности;
* переписывать расчётные функции;
* мигрировать localStorage;
* переходить на React/Vue/Angular;
* переходить на React Native/Expo;
* менять архитектуру проекта только ради моды или «современности».

## Критерии качества

Каждое новое решение должно оцениваться по вопросам:

1. Стало ли пользователю проще?
2. Уменьшилось ли количество действий?
3. Удобно ли пользоваться одной рукой?
4. Не появилась ли новая обязательная стоимость эксплуатации?
5. Сохранилась ли работа без сервера?
6. Не сломана ли существующая бизнес-логика?
7. Работает ли desktop?
8. Работает ли mobile?
9. Сохранены ли существующие данные?
10. Проходят ли тесты?
